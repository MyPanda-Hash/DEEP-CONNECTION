# 04 单据生命周期:状态机 / 审批流 / 软删审计 / 选单占用生单 / 流水号

> 能力地图 **D(单据生命周期)**。双实现互证:
> **YINJIA-MES**(`C:\INCER\YINJIA-MES`,JdbcTemplate + 物理业务表 + `yj_doc_status` 状态表)
> × **light-mes**(`E:\INCER\light-mes`,MyBatis-Plus + 统一 `form_data` 表,status 直接存表)。
> 数据键一律中文(ADR-0001:buttonName/单据状态存储值永不随语言变化)。

## 0. 设计意图

单据生命周期是 MES 的骨架:任何业务单据(采购/生产/销售/质检)都要回答「单子现在什么状态、
谁在何时把它推到此状态、能不能改」。本文给出四个可复用件:①状态机(单表推导,不散落各处
`if`);②审批流(提交→通过/驳回,留痕防伪);③软删+审计列(历史不丢、可追溯);④选单占用/生单
(防止同一来源行被两个下游重复执行)。两项目各实现一遍,差异交叉印证,选型见各节「复现要点」。

## 1. 文档状态机

### 契约(状态与推导优先级)

| YINJIA 状态 | 判据(yj_doc_status 列) | 说明 |
|---|---|---|
| 草稿 | 无行 或 全列空 | 默认态,唯一可编辑态 |
| 审批中 | `pending='Y'` | 已提交审批,不可保存 |
| 已审核 | `shr` 非空 | 生效态(生单/选单来源) |
| 已中止 | `stopped='Y'` | 仅已审核可中止;保留 shr |
| 已作废 | `canceled='Y'` | 删除单据所得,终态 |

**状态推导优先级(硬编码,不可调序):已作废 > 已中止 > 已审核 > 审批中 > 草稿。**
即 `canceled='Y'` 时即使 shr 也在也判作废。关键实现 `ButtonService.docStatusOf()`。

合法转换(越权转换一律抛 `IllegalStateException`,全局归一 409):

| 动作 | 允许源态 | 目标态 | 附加校验 |
|---|---|---|---|
| 保存 | 草稿 | 草稿 | 已审核/审批中/已中止拒绝(需先弃审/等待/恢复) |
| 提交审批 | 草稿 | 审批中 | 清 shr/shj,留痕 SUBMIT/PENDING |
| 审批通过 | 审批中 | 已审核 | 须 `requirePendingSubmission` + 审批权限 |
| 审批驳回 | 审批中 | 草稿 | 意见必填;留痕 REJECT/REJECTED |
| 弃审 | 已审核 | 草稿 | 清 shr/shj;留痕 UNAUDIT/PENDING |
| 中止 | 已审核 | 已中止 | 留痕 STOP/STOPPED |
| 取消中止 | 已中止 | 已审核(shr 在)或草稿 | 留痕 UNSTOP/UNSTOPPED |
| 删除(单据) | 草稿 | 已作废 | 已审核先弃审;触发占用释放 |

### 表结构(yj_doc_status)

```sql
CREATE TABLE yj_doc_status (
  panel_code VARCHAR(50) NOT NULL, doc_no VARCHAR(50) NOT NULL,
  shr NVARCHAR(50) NULL, shsj DATETIME NULL,                 -- 审核人/审核时间
  canceled CHAR(1) NOT NULL DEFAULT 'N', cancel_by NVARCHAR(50), cancel_at DATETIME, -- 作废
  stopped  CHAR(1) NOT NULL DEFAULT 'N', stop_by  NVARCHAR(50), stop_at  DATETIME,   -- 中止
  pending  CHAR(1) NOT NULL DEFAULT 'N', pending_by NVARCHAR(50), pending_at DATETIME, -- 审批中
  update_at DATETIME NULL, PRIMARY KEY (panel_code, doc_no));
```

light-mes 无独立状态表:`form_data.status` 直接存状态字符串,状态集多 3 个执行态
(草稿/审批中/已审核/**生产中/已完工/已关闭**/已中止),`EFFECTIVE_STATUSES = {已审核,生产中,已完工,已关闭}`
仅拦截;取消中止直接置「已审核」(无 shr 保留概念)。

### 关键代码路径

- YINJIA:`ButtonService.callButton` 按钮分发(L45-62)→ `audit/unaudit/stop/unstop/submitApproval/approveApproval/rejectApproval/delete`;
  `docStatusOf` 推导(L578-600);状态写入统一走 `MERGE yj_doc_status ... WHEN MATCHED/WHEN NOT MATCHED`。
- light-mes:`PxService.changeStatus`(L2793-2875,审核/弃审/关闭/手工完工/中止/取消中止 六分支);
  `submitApproval/approveApproval/rejectApproval`(L3120-3218);`requiresApprovalWorkflow`(L3370,
  命中 `APPROVAL_PANELS` 集合或面板 config 含审批按钮则「审核」按钮被重定向为提交审批)。

### 复现要点

1. 状态推导**单一入口**(`docStatusOf`),业务代码只读它,不做散落判断;2. 写状态一律 upsert(首次点审核
   也要建行,别直接 UPDATE);3. 每个转换只允许一个源态,拒绝信息必须点出当前状态;4. 中止 ≠ 作废:
   中止保留 shr(恢复可回已审核),作废是终态;5. 若像 light-mes 存字符串,需注意「已中止」仍允许被
   `validateSourceLinks/ensureNoEffectiveChildren` 排除在下游占用与防删除之外。

## 2. 审批流

### 契约

按钮(中文键,均走 `px/callButton`):**提交审批 / 审批通过 / 审批驳回 / 审批情况 / 弃审**;
YINJIA 另有 中止/取消中止 同链留痕。历史接口 `GET /api/px/getApprovalHistory?panelCode=&code=`
(返回 list,时间升序)。**审批通过/驳回必须紧跟一次有效提交**:`requirePendingSubmission(panelCode, formNo)`
取 `yj_form_approval` 该单 `id DESC` 第一条,必须 `action='SUBMIT' AND result='PENDING'`,
否则抛「单据尚未提交审批，不能审批通过或驳回」——防止绕过提交节点直接改状态伪造审批结果。

### 表结构(yj_form_approval)

```sql
CREATE TABLE yj_form_approval (
  id BIGINT IDENTITY, panel_code VARCHAR(50), form_no VARCHAR(50),
  action VARCHAR(20),   -- SUBMIT/APPROVE/REJECT/UNAUDIT/STOP/UNSTOP
  result VARCHAR(20),   -- PENDING/APPROVED/REJECTED/STOPPED/UNSTOPPED
  node_no INT DEFAULT 1, -- 预留多级审批
  operator NVARCHAR(50), opinion NVARCHAR(500), create_time DATETIME);
```

light-mes 对等实体 `FormApproval`(`@TableName("form_approval")`),action/result/字段结构一致。

### 关键代码路径

- YINJIA:`ButtonService.submitApproval`(L418)/`approveApproval`(L435)/`rejectApproval`(L450)/`recordApproval`(L493)/
  `queryApprovalHistory`(L505)/`requirePendingSubmission`(L474)。审批权限: `requireApprover`(L485)查
  `yj_user.is_admin='Y'`,否则 `AccessDeniedException`(403)。
- light-mes:`PxService.recordApproval`(L3094)/`requirePendingSubmission`(L3108)/`getApprovalHistory`(L3229);
  权限在 `RoleService`:`perms` 含 `audit` 才进 `approvePanels`(L324-325),admin 全面板可审批。
- 前端:`core/views/ApprovalHistoryDialog.vue`;提交/通过/驳回的 formData 仅 `{编号, 审批意见}`。

### 复现要点

1. 留痕与状态更新同事务;2. 防伪校验取**最近一条**而非任意一条;3. 驳回意见必填(前端+后端双守);
4. 审计权限独立裁决(不依赖角色面板的 view 权),YINJIA 用 is_admin、light-mes 用 can_approve,二选一即可;
5. 「审核」旧按钮在启用审批流面板自动降级为「提交审批」(light-mes `requiresApprovalWorkflow` 为妙招)。

## 3. 软删除 + 审计列

### 契约

- 业务表(含明细行)统一软删:`asp_cancel='Y'`;查询一律 `ISNULL(asp_cancel,'N')<>'Y'`。
- 审计列:`asp_user1/asp_time1` = 创建人/创建时间;`asp_user2/asp_time2` = 最后修改人/修改时间(与旧库遗留数据一致)。
- 单据删除 ≠ 软删行:单据走状态机置「已作废」;档案面板删除 = 按编码列 `DELETE` 语义的软删该档所有行。

### 关键代码路径(YINJIA `ButtonService`)

- `upsertLineRows`(L136)+ `softDeleteMissing`(L156):保存时 `liveIds` 集 = 本次在场行 id,
  事务内把 group 下不在集合的存活行置 `asp_cancel='Y'`(缺席行=被前端删掉的行)。
- `saveArchive`(L185):档案整档 upsert;**全部缺席时不清理**(`if (!liveIds.isEmpty())`,防误清整档)。
- `insertRow`(L252)填 1 号审计列、`updateRow`(L304)填 2 号;列名一律 `[列名]` 方括号包裹(列名含 %/. 等)。
- `fillRequiredDefaults`/`dropNullsOnNotNull`(L279/L337):sys.columns 元数据兜底,保证 NOT NULL 列
  有默认值、更新时 null 不写入 NOT NULL 列。

### 复现要点

1. 审计列填什么、何时填,全项目唯一约定(写死两处),后端统一,别让各面板自己拼 SQL;
2. 软删用 `ISNULL(x,'N')<>'Y'` 兼容历史 NULL;3. 明细行级 upsert 必须防「误删整表」;
4. light-mes 是物理删除(`formMapper.deleteById`),仅状态为 草稿/启用/停用 可删——若选物理删,须保
   `ensureNoEffectiveChildren`(L3022)拦截「已被下游使用」。

## 4. 选单占用 / 生单(两种实现,选型关键)

### 实现 A:light-mes —— 无占用表,全库反查

来源信息写在**目标单明细行**上:来源面板/来源单号/来源行号。校验链路:
`validateSourceLinks`(L2913,审核/提交时逐行校验:来源存在、`EFFECTIVE_STATUSES` 有效、行号存在、
`localKeys` 防同一来源行重复选入、`reservedQuantity` 为 0、`current+reserved <= limit` 超量拒绝)→
`reservedQuantity`(L2952,**遍历全部 `form_data`**,排除自身单与「已中止」,按 来源面板/单号/行号 累加
执行数量)→ `refreshSourceExecution`(L3035,审核后把 累计执行数量/累计检验数量/累计入库数量 回写
来源单明细,非状态存储)→ `ensureNoEffectiveChildren`(L3022,弃审/删除前全库反查下游)。
生单:`PxService.callButton` 里 ~20 个硬编码 `createXxx(SO→MO / MO→PROCESS_REPORT / PU_REQ→PU_ORDER …)`,
头/行字段逐个手写(L1408-2650)。
**代价:每次校验 O(全部单据×明细);两用户并发可选同一来源行(写入前无锁)。**

### 实现 B:YINJIA —— `form_flow_link` 持久化(推荐)

```sql
CREATE TABLE form_flow_link (
  id BIGINT IDENTITY, source_panel_code, source_form_no, source_detail_key, source_line_key,
  target_panel_code, target_form_no, target_detail_key, target_line_key,
  inventory_code, source_quantity DECIMAL, linked_quantity DECIMAL,
  link_status CHAR(8),  -- ACTIVE / RELEASED
  create_by NVARCHAR(50), release_time DATETIME);
```

- `VoucherFlowService.sources`(L39):选单列表 = 已审核单据 + 占用过滤——`loadConsumed` 按
  `source_panel_code+target_panel_code` 分组 `SUM(linked_quantity) WHERE link_status='ACTIVE'`,
  每行算 `_lineKey / 已生单数量 / 剩余数量`,剩余 > 0 才出现在选单(行级剩余量,SQL 聚合 O(占用数))。
- `VoucherFlowService.link`(L75):生单/选单后按 `targetOffset` 把来源行与目标行一一对应 INSERT ACTIVE。
- `VoucherFlowService.release`(L96):`UPDATE ... link_status='RELEASED', release_time=SYSDATETIME()`
  由 `ButtonService.delete`(L536)调用(下游草稿作废 → 来源行重新可选,**释放留痕**)。
- `PushGenerateHandler`(整单生单):与选单**共用** `PanelConfigService.flowMaps(target)` 的
  `headerMap/detailMap`(SELECT_FLOWS 链路图,同一份映射双向使用);`supports()` 按
  `configService.pushTarget(panelCode, action)` 判定;守护:来源必须「已审核」+ 该来源→目标已有
  ACTIVE 占用则拒绝重复生单;返回 `{编号, 单据状态, gotoPanel}` 由前端跳转继续填写。
- 接口:`POST /api/px/voucherFlow/sources`、`POST /api/px/voucherFlow/link`(PxController L51/L63)。
- 数量/存货字段候选(`VoucherFlowService.QTY_FIELDS/INV_FIELDS`):数量/实收数量/计划数量/派工数量/
  需用数量/领料数量;存货编码/产品编码/材料编码/物料代码。

### 选型建议

**推荐 B(持久化)**:占用/剩余是行级 SQL 聚合,面板增多不劣化;release_time 留痕可审计;并发下
"两用户选同源行"天然串行化(唯一索引约束可再加:source+target+status)。A 适合面板 <10 的原型,
但必须补齐:来源三键、下游有效状态排除、同源重复行校验、超量校验、下游拦截——A 事实上把这套
逻辑写进了 PxService 单文件 2000+ 行,维护成本高。

### 复现要点

1. 占用粒度 = 来源面板+来源单号+来源行键(行键含 `docNo#id`,无 id 用 identityHashCode 兜底);
2. 释放入口挂「删除/作废下游」,释放=状态变更非物理删,留 release_time;
3. 所选行写入时带 `_lineKey/已生单数量/剩余数量` 回显,前端可读;4. 生单与选单必须共用同一份头/行映射,
   杜绝两套映射漂移;5. 量字段用候选名列表按面板习惯命中,别硬编码单字段名。

## 5. 流水号(前缀 + yyMMdd + 4 位序号)

YINJIA `FormNoService`(s_allno 号池,与旧系统一致):

- `next(prefix, user)`:查 `s_allno` 中 `lb=前缀 AND ny=yyMMdd AND LEN(dh)>=10` 的
  `MAX(CAST(RIGHT(dh,4) AS int))`,下一位 = max+1,生成 `前缀+yyMMdd+%04d`(如 `RK2608290001`);
- `exists()` 双表查重(`s_allno.dh` ∪ `inh.inh_no`),冲突则序号递增重试;
- 每次取号 INSERT 一行留痕(comm/lb/ny/asp_user1/asp_time1/asp_cancel);
- `preview(prefix)`:只算不写(新建表单默认值展示用,不消耗号池)。
- 注意:`LEN(dh)>=10` 过滤异常脏数据;`RIGHT(dh,4)` 取序号依赖「日粒度唯一前缀」约定。

light-mes `PxService.generateFormNo`(L3294):硬编码 ~40 个面板前缀表(SO-/MO-/RK-/CK-…),
格式 `前缀-yyyy-MM-dd+2 位当日序`(如 `MO-2026-08-1701`),每天从 01 开始,`form_data` 精确查重。

### 复现要点

1. 号池表(前缀/日/号/留痕列)+ 单日 `max(序号)+1`,唯一索引兜底,冲突重试循环;2. 固定位数
(4 位)便于排序与肉眼识别;3. `preview` 与 `next` 分离是前端体验关键;4. light-mes 每面板一个前缀
数组可行但加面板必须改码——建议前缀也入面板元数据(prefix 字段)。

## 6. 验收锚点(实现后最小通过动作)

1. 新单保存→提交审批→审批通过:状态 草稿→审批中→已审核,`yj_form_approval` 3 条留痕(SUBMIT/APPROVE);
2. 不提交直接调「审批通过」→ 409「单据尚未提交审批…」;3. 已审核单点保存 → 拒绝;弃审 → 回草稿可改;
4. 来源单已审核,「生单」2 张下游草稿:选单列表该单剩余=0;删除 1 张 → 剩余恢复、`link_status=RELEASED`;
5. 保存时删掉 1 条明细行 → 该行 `asp_cancel='Y'` 而 `asp_user2/time2` 已更新。
