# 09 双实现差异与选型（light-mes × YINJIA）

> 前置：00 总盘点 A2/F7 差异表与本文互为表里；本文回答「为什么不同、什么时候用哪个、如何混合」。
> 基线：light-mes（E:\INCER\light-mes，真源 f850839，MySQL light_mes）= **MyBatis-Plus + FormData JSON 单表**；
> YINJIA-MES（C:\INCER\YINJIA-MES，SQL Server HSDZ_MES）= **JdbcTemplate + 业务物理表**。
> 关键共同点：两项目**前端面板引擎同构**（px 契约 `getPanelConfig/getPermMatrix/getNewFormPermMatrix/getFormDescriptor/queryFormDataList/callButton/deleteForms/saveColumnPrefs`，配置结构 `metadata/panelPageDto/dataSchema/detail` 对齐）——差异全部在后端数据层与个别交互，前端选型二选一不成立。

### 基线对比

| 维度 | light-mes | YINJIA-MES |
|---|---|---|
| 数据库 | MySQL `light_mes` | SQL Server `HSDZ_MES` |
| ORM | MyBatis-Plus（`mybatis-plus-spring-boot3-starter`+jsqlparser） | 无 ORM，全 `JdbcTemplate`（`spring-boot-starter-jdbc`） |
| 数据表 | `FormData` 单表（detailData JSON）+ `panel_config` | 业务物理表 + `yj_panel/yj_field` 元数据 |
| 状态 | `FormData.status` + Java 常量（`EFFECTIVE_STATUSES`） | `yj_doc_status` + 工作流注册表推导 |
| 审计 | 无原生审计列，Java 记 | `asp_user1/asp_time1/asp_time2/asp_cancel` 列原生 |
| 翻译 | `sys_translation/sys_locale`，前端 tt 兜底 | `yj_translation/yj_locale`，后端配置翻译 |
| 占用 | 无表，`reservedQuantity()` 反查 | `form_flow_link`（ACTIVE/RELEASED） |
| 部署 | init.sql + nginx | 迁移清单 + DbSync + 单 jar |

## 1. 数据层：FormData JSON 单表 vs 业务物理表

### light-mes（MyBatis-Plus + JSON）

- 依赖：`mybatis-plus-spring-boot3-starter` + `mybatis-plus-jsqlparser` + `mysql-connector-j`（`backend/pom.xml`）。
- 数据：统一 `FormData`（`panelCode/formNo/status/detailData JSON`）单表；面板配置 `panel_config` + 各 Registry（`MenuPanelRegistry/QualityPanelRegistry/ReportPanelRegistry/SalesFinancePanelRegistry` + `PanelRegistry`）。
- **扩展易**：加面板 = 插行 + JSON 字段，零 DDL；报表聚合走 SQL 视图 / Java 聚合（`ReportQueryService` + `ReportPanelRegistry`）。
- 代价：无强类型、无字段约束、无外键；状态/审计靠 Java（`FormData.status` + `EFFECTIVE_STATUSES`）；字段级校验在 `PxService` 内手写；跨表 join 不可行（需视图固化）。

### YINJIA（JdbcTemplate + 物理表）

- 依赖：`spring-boot-starter-jdbc`；全部 service 用 `JdbcTemplate`（`QueryService/PanelConfigService/ButtonService/VoucherFlowService/PushGenerateHandler/TranslationService/PanelRegistry…`，无 ORM）。
- 数据：业务物理表（`bd_/bl_` 风格）+ 元数据 `yj_panel/yj_field` + 状态 `yj_doc_status` + 翻译 `yj_translation/yj_locale` + 占用 `form_flow_link` + 审计列（`asp_user1/time1/2/asp_cancel`）与流水号列（`s_allno`）。
- **强类型/约束/审计原生**：库级约束、索引、审计留痕、事务由 SQL 承担；加面板 = 建表 + `yj_panel/yj_field` 插行 + 迁移脚本进 `db-migrations.txt`。
- 代价：面板量大时迁移脚本重（已有 `fix-missing-columns.sql` 等修复脚本兜底）；半结构扩展需 `ALTER TABLE` + 元数据同步。

### 影响对照

| 维度 | light-mes（JSON） | YINJIA（物理表） |
|---|---|---|
| 加面板成本 | 插行 + JSON 字段 | 建表 + 元数据 + 迁移脚本 |
| 数据完整性 | Java 校验，库无约束 | 库约束/索引/审计列原生 |
| 报表/聚合 | 视图 + Java 聚合 | 视图直映表结构，可建索引优化 |
| 类型安全 | 弱（JSON 字符串） | 强（类型映射 + 库约束） |
| 半结构扩展 | 随意加键 | 需 ALTER + 元数据同步 |
| 跨库 join | 不可 | 直接 join 业务库 |

**关键位置**：light-mes `backend/src/main/java/com/mes/service/PxService.java`、`panel/PanelRuntimeService.java`、`resources/db/init.sql`；YINJIA `backend/src/main/java/com/yinjia/mes/service/{QueryService,PanelConfigService,PanelRegistry}.java` + `tools/migrate-*.sql`。

## 2. 占用与生单：无表反查 vs form_flow_link 持久化

- **light-mes（无表反查）**：`PxService.reservedQuantity()`（约 line 2952）——`formMapper.selectList` 遍历**全部 FormData** → 排除目标单自身、跳过「已中止」→ 按明细行「来源面板/来源单号/来源行号」匹配，累加 `executedQuantity`。无占用表、无显式释放（靠「下游已中止排除」软过滤）；性能 O（全部单据 × 明细）。生单映射为每对面板硬编码 `generateXxx`（PxService 内约 20 个，头/行字段逐个手写）。
- **YINJIA（form_flow_link 持久化）**：`tools/migrate-form-flow-link.sql` 建表——`source/target`（`panel_code`、`form_no`、`detail_key`、`line_key`）+ `inventory_code` + `source_quantity/linked_quantity` + `link_status`（`ACTIVE/RELEASED`）+ `create_by/create_time/release_time`；索引 `idx_ffl_source/target/status`。
  - `VoucherFlowService.sources`：全量查 → Java 侧过滤「已审核」（状态由工作流注册表推导，物理列可能滞后）→ 叠加 `form_flow_link` 已占用 → 输出 `_lineKey/已生单数量/剩余数量`，剩 0 剔除；`link` 生单后写 ACTIVE；`release` 由 `ButtonService` 删除下游草稿钩子 `UPDATE ... RELEASED + release_time`（留痕）。
  - `PushGenerateHandler`（`panel.PanelActionHandler`）：推式生单（生成XX）——来源单整单映射目标面板草稿、写占用、`form_flow_link` COUNT 防重复，返回 `{编号, gotoPanel}`；`supports()` 按 `pushTarget` 判定，面板对（动作→目标）可配置，**与选单共用同一份头/行映射（双向复用）**。
- **影响**：反查零建表、改面板零联动，但全库扫描且无释放留痕；持久化 SQL 索引查询、行级剩余数量、删除留痕可审计，代价是建表 + 生单/删除钩子 + 面板对配置。

**关键位置**：light-mes `PxService.reservedQuantity()`（约 line 2952）与 `generateXxx` 系列；YINJIA `service/VoucherFlowService.java`、`panel/PushGenerateHandler.java`、`tools/migrate-form-flow-link.sql`。

## 3. 列自定义：全局元数据 vs 用户级

- **YINJIA（全局）**：`/px/saveColumnPrefs` → `PanelConfigService.saveColumnPrefs(panelCode, columns)`：按 label 定位字段 → `UPDATE yj_field SET seq=(i+1)*10, alias, visible WHERE panel_code=? AND col_name=?` → `registry.reload()`。本质是**改面板字段定义**，所有用户共享；再次调序 = 覆盖元数据基线。
- **light-mes（用户级）**：独立偏好表 `px_column_pref`（`panel_code, owner, col_name, seq, alias, visible, update_by`；`owner=''` 预留全局默认），`PanelRuntimeService.applyColumnPrefs` 在**配置读取出口**按登录用户叠加（重排/过滤/追加新列；未认证不叠加），`PxService` 保存（`DELETE + INSERT` owner 维度），前端 `ColumnPrefsDialog`。
- **建议：用户级**。理由：元数据表回答「面板是什么」，列偏好回答「用户怎么看」——混在一起后（1）调序不可逆，无基线可对照；（2）面板报错难排查（字段定义被用户改过）；（3）多用户/多账套互踩。全局需求（按角色默认列序）用 `owner=''` 行表达即可，不侵入元数据。

**关键位置**：YINJIA `PanelConfigService.saveColumnPrefs`（约 line 925）+ `PxController /px/saveColumnPrefs`；light-mes `px_column_pref`（`resources/db/init.sql` 约 line 789 + `tools/update-2026-09-01-c-column-prefs.sql`）、`PanelRuntimeService.applyColumnPrefs`、`PxService` 保存分支、前端 `ColumnPrefsDialog`。

## 4. 面板名翻译：前端 tt 兜底 vs 后端配置翻译

- **light-mes（前端兜底）**：菜单标题渲染 `tt(node.title)`；非中文时 `LeftNav.vue` watch `localeStore.current` → `ensureDict` **预取全部菜单标题词条**（库表词典/机翻补齐）；面板名/字段显示名以前端 tt 为主，后端词典为辅。
- **YINJIA（后端配置翻译）**：`PanelConfigService` 请求时按 `LocaleContextHolder`（Accept-Language）解析语言：`fieldDict()=translations.scope(locale,'field')`、`panelDict()=translations.scope(locale,'panel')` → 生成配置时 `displayName/columnAliases/panelName/页签名` 直接替换（字段别名 `alias` 优先，缺省回退中文）；`TranslationService` 30s per-locale 缓存；数据键（`dataName/buttonName/状态值`）永不翻译（ADR-0001）；前端 tt 只兜底剩余 UI 文案。
- **影响**：前端兜底语言切换即时（本地重渲），但词条量大时首屏需拉取（机翻有延迟）、词条分散于语言包与翻译表两处；后端翻译一次生成即多语言，但只覆盖面板名/字段/页签，UI 文案仍靠前端。
- **组合建议**：翻译表（scope=panel/field）做词条事实源（加行不加列）+ 前端 tt 兜底 UI 文案 + 后端配置翻译面板名/字段——三者叠加不互斥（YINJIA 即此组合）。

**关键位置**：light-mes `layout/LeftNav.vue`（`ensureDict` 预取标题）+ `stores/locale.js`；YINJIA `service/PanelConfigService.java`（`fieldDict/panelDict`）+ `service/TranslationService.java`（30s per-locale 缓存）+ `controller/LocaleController.java`。

## 5. 选型建议表

| 场景 | 选型 | 理由 |
|---|---|---|
| 快速原型 / 面板极多且杂 / 无专职 DBA | light-mes（JSON 单表） | 加面板零 DDL，迭代最快 |
| 单据类核心业务（强类型/约束/审计/流水号） | YINJIA（物理表） | 库级约束 + 审计列 + 审批状态原生 |
| 跨表报表 / 聚合统计 | 物理表 + 视图（YINJIA） | 索引可调优；JSON 只能用视图固化解法 |
| 首日即多语言上线 | 后端配置翻译 + 翻译表（YINJIA 模式） | 面板名/字段随配置翻译，不为每语言维护面板副本 |
| 团队小 / 单机演示 / 无运维 | light-mes + init.sql | 一条基线脚本，工具链最少 |
| 需与其他业务库 join / 数据开放给外部 | 物理表 | FormData JSON 无法直接 join |
| 列自定义 | **用户级 px_column_pref 模式**（对哪套后端都适用） | 不污染元数据；`owner=''` 行承载角色默认 |
| 占用/生单量大、高频 | form_flow_link 持久化 | 索引查询 + 行级剩余 + 释放留痕 |
| 占用少量 / 原型阶段 | 反查模式 | 零建表，改面板零联动 |
| 报表列设置 | `px_report_column_settings`（报告列设置/别名/自动合计） | 独立于面板字段定义（两项目均有） |

## 6. 如何混合（缝合法）

1. **前端不换**：两项目前端契约同构（px API + 配置结构一致），换后端即换数据层——YINJIA 本身就是「light-mes 前端 + SQL Server 物理表后端」的实证。
2. **渐变迁移**：新面板先 JSON 快速上线，稳定后迁物理表（单据/审计类优先）；迁移 = 建表 + 导数据 + 元数据插行，面板引擎元数据驱动（`yj_field` 可生成 DDL 列清单）。
3. **词条统一**：翻译表（scope=panel/field）为事实源 + 前端 tt 兜底（见 §4），任意语言加行不加列。
4. **列偏好直接抄表**：`px_column_pref` 表结构原样落地（面板→替换表名即可），成本一天内。
5. **一句话判据**：架构选 JSON，业务选物理表；**沉淀层**（元数据/翻译/占用/审计）用可追溯表，**展示层**（列偏好）用用户级表。

### JSON → 物理表迁移步骤（面板级）

1. 建表：按面板字段清单生成 CREATE TABLE（类型/约束/审计列 `asp_user1/asp_time1/asp_time2/asp_cancel` + 流水号列 `s_allno` 风格），挂 `db-migrations.txt`。
2. 导数据：存量 `form_data` 行转换（JSON 列 → 物理列），脚本化 + 抽样对账。
3. 元数据：`yj_panel/yj_field` 插行（scope=panel/field 译名同步补），面板名/标签与 JSON 版本一致。
4. 功能回归：`audit-panels.ps1` + `audit-conditions.ps1` 全量跑（见 08 第 3 节），旧面板名保留别名过渡。
5. 下线：双写/双跑一段时间后停用 JSON 面板（前端菜单路由不变，只换 panelCode 指向）。

### 常见翻车点

- **数据键漂移**：迁移时把中文数据键（`dataName/buttonName/单据状态`）改英文——违反 ADR-0001，前端控件与权限矩阵全部对不上。
- **列自定义写回元数据**：用户调序直接 UPDATE `yj_field`——全局污染，应改 `px_column_pref` 用户级叠加。
- **占用语义半套**：只移植 `form_flow_link` 写占用、漏掉删除下游草稿的 release 钩子——来源行永久不可选。

## 验收锚点

- 能说清本项目属于哪种数据层，并说出对应加面板的 3 步动作（JSON：插行；物理表：建表+元数据+迁移脚本）。
- 占用语义可回答：`reservedQuantity` 与 `form_flow_link` 各自的时间复杂度与「释放」如何实现。
- 列自定义不写进元数据表（用 `px_column_pref`）——审计 `yj_field.seq/alias` 未被用户操作修改。
- 切换 en 后：面板名/字段经后端翻译表出英文，剩余 UI 文案经前端 tt 兜底，无中文残留。
