# 05 组织权限审计:部门树 / 角色×面板×11 动作 / JWT / 使用审计

> 能力地图 **E(组织/权限/审计)**。双实现互证:
> **YINJIA-MES**(`C:\INCER\YINJIA-MES`,JdbcTemplate,表前缀 yj_) × **light-mes**
> (`E:\INCER\light-mes`,MyBatis-Plus,表前缀 sys_)。YINJIA 的 `SysAdminController` 明确
> 「照搬 light-mes OrgAdmin 契约」,两项目契约面同构,本文以 YINJIA 路径为主、light-mes 差异注解。

## 0. 设计意图

组织/权限/审计是「谁能用哪块、能做什么、做过什么」三问的落点。本文给出:①部门树+用户+角色
的基础组织模型;②角色×面板×11 项操作权限矩阵(加面板=授权行,零注册);③JWT 无状态认证链 +
全局异常归一(前端拿到稳定的语义化错误);④使用审计(登录+面板业务动作埋点,admin 按账号分组查看)。
权限模型决策:**admin(is_admin) 恒全权限;普通角色按面板授权,权限码逗号分隔存储;audit 码即审批权。**

## 1. 组织架构:部门树 + 用户 + 角色

### 契约(`SysAdminController`,均包 `ApiResult`)

| 接口 | 动作 |
|---|---|
| `GET /api/sys/dept/tree` | 部门树(Java 侧parent_id 组树,roots 数组) |
| `POST /api/sys/dept/save` | 新增/更新部门(名称必填,parentId 缺省 0) |
| `DELETE /api/sys/dept/{id}` | 删除部门(有下级部门/有用户 → 409 拦截) |
| `GET /api/sys/user/list` | 用户列表(LEFT JOIN 部门/角色名,isAdmin 由 is_admin 派生) |
| `POST /api/sys/user/save` | 新增/更新用户;空密码=不改密码;新建必须设密码,账号唯一 |
| `GET /api/sys/role/list` | 角色列表(roleCode/roleName/remark/isAdmin) |
| `POST /api/sys/role/save` | 新增角色(编码唯一;角色默认非 admin) |
| `DELETE /api/sys/role/{id}` | 删角色(先删 `yj_role_panel`,有用户 → 409 先调整) |

### 表结构

```sql
yj_dept(id, parent_id, dept_name, sort)
yj_user(id, username UNIQUE, password_hash, real_name, is_admin CHAR(1),
        dept_id, role_id, enabled CHAR(1))                -- is_admin 随角色派生
yj_role(id, role_code UNIQUE, role_name, remark, is_admin CHAR(1))
```

light-mes 对等实体:`SysDept(sys_dept)`/`SysUser(sys_user)`/`SysRole(sys_role)`,
角色 CRUD 在 `RoleService.saveRole/deleteRole`(管理员角色不可改/不可删,`is_admin=1` 的 role
直接拒绝;删角色时把该角色下用户 role_id 置空再删授权)。

### 关键文件

- YINJIA:`controller/SysAdminController.java`(全部接口 + `PERMISSION_ACTIONS`)、`AuthController.java`
  (登录;首次启动自动种子 `admin/123456`)、`config/SecurityConfig.java`。
- light-mes:`service/RoleService.java`、entity 包 `SysDept/SysUser/SysRole/SysRolePanel`。

### 复现要点

1. 密码只存 BCrypt hash(`PasswordEncoder`),登录用 `matches`;**校验与改动都只在 service 层**,别在
   Controller 拼 SQL;2. 新建用户必填密码、账号唯一:先 COUNT 后 INSERT(并发靠唯一索引兜底);
3. 删除守卫三连:部门→查子部门/用户;角色→查用户;先删授权后删角色;4. `is_admin` 与角色联动:
   角色 admin → 用户 is_admin='Y',权限随角色走,避免用户级再来一个开关造成双源。

## 2. 角色 × 面板 × 11 项操作权限

### 契约

权限码共 **11 项,顺序即前端矩阵列序**(YINJIA `SysAdminController.PERMISSION_ACTIONS`):

`view`可见 / `query`查询 / `add`新增 / `edit`修改 / `delete`删除 / `export`导出EXCEL /
`print`打印预览 / `audit`审核反审核 / `price`价格金额 / `review`复核反复核 / `adjust`调价
(light-mes `RoleService.PERMISSION_ACTIONS`:查看/查询/新增/修改/删除/导出/打印/审批/价格/复核/调整;
`review/adjust` 为预留位,暂无对应按钮)。

- `GET /api/sys/role/{id}/panels` → `{modules(按 panel.module_group 分组,含 panels[]), allPanels,
  granted[{panelCode, perms}], actions}`;
- `POST /api/sys/role/{id}/panels` → 全删重插:`(role_id, panel_code, perms, can_approve)`,
  `can_approve = perms 含 "audit" ? "Y" : "N"`(保持旧链路兼容);
- 运行时:`getPermMatrix` / `getNewFormPermMatrix`(px 契约)按面板返回授权矩阵与按钮可用性。

### 表结构

```sql
yj_role_panel(role_id, panel_code, perms NVARCHAR,  -- 逗号分隔,如 "view,query,audit"
              can_approve CHAR(1))                  -- 由 audit 派生
```

light-mes 对等:`sys_role_panel(role_id, panel_code, perms, can_approve)`。

### 关键文件

- YINJIA:`SysAdminController`(L218-275,授权保存/读取)、`PanelRuntimeService`(getPermMatrix 等)。
- light-mes:`RoleService.java` —— `normalizePerms`(**过滤非法码、去重、view 置首**:有任意权限必含
  view,L199-217)、`permsOfRow`(存量行 perms 为空时按 can_approve 回退 `view` / `view+audit`,L220)、
  `getPerms`(按用户算 `{isAdmin, roleCode, visiblePanels, approvePanels, panelPerms}`,**TTL 30s 缓存**,
  授权/角色/用户变更 `invalidatePermCache`,L280-295)、`listPanels`(TTL 60s)、`getRolePanels/saveRolePanels`。
- admin 语义:`is_admin=1` 用户 → 可见全部面板 + `hasApproval` 面板全进 approvePanels(L312-317)。

### 复现要点

1. 11 码是**枚举**,不是自由字符串;2. view 恒有(能看才能干别的);3. `audit` 是审批权的唯一来源
   (can_approve 由其派生,别存两处);4. 授权保存=先清后插(简单幂等);5. 权限计算加 30s 缓存,
   写路径显式失效,否则授权后要等缓存过期;6. 面板清单带 `hasApproval`(由面板按钮组是否含
   审批通过/提交审批 推得),审批面板与普通面板在前端交互上分道。

## 3. JWT 认证链 + 全局异常归一

### 契约

- **链**:请求 → `JwtAuthFilter`(Bearer 解析)→ `SecurityContext` 注入 → Controller 业务;
  `SecurityConfig` 无状态(STATELESS,不建会话);`Authentication.getName()` = 用户名,system 兜底。
- **白名单**:`OPTIONS /api/**`、静态资源(`/`, `/index.html`, `/favicon.ico`, `/assets/**`, `/vite.svg`)、
  `/api/auth/login`、`/api/base/factory/list`、`/api/locale/list`、`/api/locale/dict`;其余一律
  `.anyRequest().authenticated()`。未认证/无权限统一 `res.sendError(403, "未认证"/"无权限")`。
- **返回值**:`ApiResult{code, message, data}`,成功 `code=200`;异常归一如下 ——

| 异常 | HTTP 状态 | body |
|---|---|---|
| `IllegalArgumentException`(参数) | 400 | `{code:400, message}` |
| `IllegalStateException`(业务冲突) | **409** | `{code:409, message}` |
| `Exception`(兜底) | 500 | `{code:500, "服务异常："+msg}` |
| `AccessDeniedException`、`OcrServiceException`、`OcrRateLimitException` | 200(body-code) | `fail(403/503/429)` |
| 上传类(MaxUploadSizeExceeded/Multipart/MissingPart/MissingParam) | 200(body-code) | `fail(400, …)` |

> 设计点:403/429/503 走 **body-code** 而非 HTTP 403,避免前端 axios 统一把 HTTP 403 当「登出」
> 触发跳转登录;4xx 业务错(400/409)保留真实 HTTP 状态供调用方分支。

### 关键文件

- `config/SecurityConfig.java` —— `filterChain`(白名单/无状态/过滤器位置/异常入口)。
- `config/JwtAuthFilter.java` —— `Bearer ` 前缀 → `jwtUtil.validate` → `UsernamePasswordAuthenticationToken
  (username, null, [ROLE_USER])`;校验失败静默放行(由 Security 的 authenticated 拦)。
- `config/JwtUtil.java` —— HMAC-SHA:`Keys.hmacShaKeyFor(secret≥32 字节,不足补零)`,
  `yinjia.jwt.secret` + `yinjia.jwt.expire-hours`(默认 24h),subject=用户名。
- `controller/AuthController.java` —— `POST /api/auth/login`:`yj_user.password_hash` BCrypt matches →
  `{token, user{userName,realName,roleCode,isAdmin,visiblePanels,approvePanels}}`;失败
  `IllegalStateException("用户名或密码错误")`(不区分账号不存在,防枚举);登录成功记使用记录(失败不记)。
- `config/GlobalExceptionHandler.java` + `dto/ApiResult.java`;前端 `core/request.js` 统一取 message。

### 复现要点

1. 无状态 + 白名单最小化(登录/语言/工厂基础接口即可放开,其余全走令牌);
2. secret 配置化、≥32 字节随机,过期 24h 可配;3. 过滤器失败**不主动响应**,让 Security 的
   `authenticationEntryPoint` 统一 403(与全局异常体隔离);4. 归一规则写死在一处,业务层只管抛
   `IllegalArgumentException/IllegalStateException`,不许自己拼 400/409 响应;5. 403/429 类必须
   走 body-code 且与「未登录」在语义上可区分(前端只对「未认证」登出)。

## 4. 使用审计(登录 + 面板业务动作)

### 契约

- 埋点两条:①登录成功 `recordLogin(userName, realName, ip)`(失败不记);②面板业务动作
  `recordAction(userName, realName, panelName, actionName, docNo, ip)` ——
  `POST /api/px/callButton` 与 `/deleteForms` **成功后**记录;`刷新/查找` 等纯浏览动作
  (`VIEW_ONLY_BUTTONS = {刷新, 查找}`)不记录;埋点失败静默(日志是旁路事实,不影响主流程)。
- 查询(admin-only,调用方 `requireAdmin()` 校验 `yj_user.is_admin='Y'`):
  `GET /api/sys/usageLog`(分页 rows+total,条件可空即不过滤,时间倒序);
  `GET /api/sys/usageLog/grouped`(按账号分组 `groups[{userName, realName, total, rows[]}]`,
  组序=各组最新一条倒序即活跃度在前,上限 2000 条)。

### 表结构

```sql
yj_usage_log(id, user_name, real_name, event_type CHAR(6),  -- login / action
             panel_name, action_name, doc_no, ip, created_at)
```

### 关键文件

- YINJIA:`service/UsageLogService.java`(recordLogin/recordAction/query/queryGrouped;写入 try-catch 静默)、
  `controller/PxController.java`(L141-177 埋点:`recordUsage`,按钮名/单据号取 `formData` 的
  `编号/单据编号/记录编号`,面板名回退 panelCode)、`controller/AuthController.java`(L53 登录埋点)、
  `controller/SysAdminController.java`(L42-77 查询接口+requireAdmin)、前端 `views/sys/UsageLog.vue`。

### 复现要点

1. 埋点在**成功路径**且 try-catch 包住——审计绝不能拖垮业务;2. 明确「哪些动作不算使用」
   (查询/刷新/列调整),否则表被刷屏;3. 查询接口必须独立 admin 守卫(不能只依赖角色面板授权,
   无面板授权的用户可能仍要查);4. 分组查询限流(TOP 2000)防全表灌进内存;
5. event_type 用登录/动作二分即可,面板动作细度=按钮名,足够审计与排障。

## 5. 验收锚点

1. 新建角色 → 授权 3 个面板(勾 view/query/audit)→ 该角色用户登录:可见 3 面板、可提交审批+审批、
   无加/改/删权;2. 直接调 `POST /api/sys/role/{id}/panels` 后 30s 内新权限即时生效(缓存失效);
3. 无 token 访问业务接口 → 403「未认证」且前端不跳登出;密码错误 → 409 文案「用户名或密码错误」;
4. 登录 1 次 + 点 2 次「保存」→ 使用记录 3 条(1 login + 2 action,含单据号与 IP);
5. 非 admin 调 `/api/sys/usageLog` → 403「仅管理员可查看使用记录」。
